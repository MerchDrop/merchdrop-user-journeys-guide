```ts
import * as Sentry from '@sentry/react';

export const initSentry = () => {
  Sentry.init({
    dsn: import.meta.env.VITE_SENTRY_DSN,          // reads from .env
    environment: import.meta.env.MODE,              // 'development' or 'production'
    integrations: [Sentry.browserTracingIntegration()],
    tracesSampleRate: 1.0,
    beforeSend(event) {
      // IMPORTANT: dev events are filtered out here — this is intentional.
      // Testing Sentry in dev will show nothing in the dashboard. That is correct behavior.
      if (import.meta.env.MODE === 'development') {
        return null;
      }
      return event;
    },
    beforeBreadcrumb(breadcrumb) {
      if (breadcrumb.category === 'console' && import.meta.env.MODE === 'production') {
        return null;
      }
      return breadcrumb;
    },
  });
};

export const SentryErrorBoundary = Sentry.withErrorBoundary;
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser bundle → Sentry ingest | DSN is ingest-only; not an authentication credential. Exposure is accepted Sentry design. |
| App startup → Sentry initialization | Sentry must be initialized before React mounts to capture early render errors |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Information Disclosure | VITE_SENTRY_DSN in client bundle | accept | Sentry DSN is ingest-only (write, not read). Rate-limited. This is the standard Sentry deployment model; not a secret |
| T-02-02 | Denial of Service | Sentry event flooding | accept | tracesSampleRate: 1.0 is fine for initial activation; can be reduced if volume becomes an issue post-launch |
| T-02-03 | Tampering | Sentry events spoofed from non-app sources | accept | DSN is ingest-only; spoofed events add noise but cannot exfiltrate data |
</threat_model>
